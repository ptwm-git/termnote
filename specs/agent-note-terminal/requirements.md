# TermNote · 终端笔记：需求与验收标准

> 0.3.0 用户修正（2026-10-19）优先于下文 0.1/0.2 的旧版交互：右侧原生侧栏、上备份下终端，新标签默认系统 Shell；当前文档作为来源，备份另建同目录文件。R11—R14 定义本轮验收。R9/R10 的 Agent 管理与 OpenCode 增强仅保留旧会话兼容，不作为新会话默认入口。

日期：2026-10-18。状态：0.2.0 功能已实现，当前 0.2.2 已公开发行，社区目录已提交；实际通过范围见 [验证记录](../../docs/VALIDATION.md)。

本文是该独立插件的需求正文。当前已有源码和 0.2.2 公开发行版；具体通过情况以验证记录为准，不能把需求条目本身当成通过证据。

## 1. 用户目标与场景

用户希望在 Obsidian 的一篇 Markdown 笔记中启动终端，运行自己安装的 Agent，持续输入并查看结果。命令和终端显示的内容应自动保存到这篇笔记，关闭页面后仍能阅读、搜索、引用。换一篇笔记，可以拥有另一个独立会话。

插件窗口还应提供浏览器式多标签，让用户同时进行多个独立对话。每个标签对应当前文件夹中的一个真实 Markdown 文件。点击新增标签时，自动创建同目录新文件；默认使用“终端页面一、终端页面二、终端页面三……”递增命名，用户可以自行修改文件名。

用户已确定：

- 名称为「终端笔记」，英文 TermNote；插件 ID 沿用 `agent-note-terminal`，更名不迁移现有会话或日志。
- 只支持 PC：Windows、macOS。
- 做一个专门的独立插件。
- 任意 Agent、一页一会话、自动持续保存、关闭后仍有完整可读笔记。
- 插件内可打开多个标签并切换使用，每个标签对应一个文件和独立会话。
- 新标签对应当前文件夹中新建的文件，默认递增命名，支持用户重命名。

用户已表示“你可以开始开发了”；下文已说明的保存时限、关闭行为、首次调用与目录选择细节、兼容边界作为首版默认方案采用。Windows 与未实测的交互项目仍需按验证清单验收。

## 2. 关键术语与承诺边界

- **Shell**：执行命令的程序，例如 Windows 的 PowerShell、macOS 的 zsh。
- **PTY（伪终端）**：让程序获得真实终端所需的键盘交互、窗口大小和光标控制能力。
- **通用模式**：通过可配置的命令启动本机命令行程序，不限定 Agent 品牌。程序仍须兼容本机系统及所提供的终端能力。
- **原始会话日志**：按顺序保存终端输出、时间和终端尺寸等回放所需事件，不以当前屏幕或有限滚动历史代替日志。
- **可读笔记**：去除终端控制符并处理重绘后写入 `.md` 的文字记录；无需插件也能阅读。
- **结构化对话**：精确区分用户提问、Agent 回答与工具调用的记录。通用终端流并不保证包含这些语义，需要 Agent 提供相应日志或协议才能准确实现。
- **终端标签**：插件窗口内部的会话标签。每个标签映射一篇真实笔记和一个逻辑会话，可在 Obsidian 自身的页面标签中承载；不是仅存在于内存中的临时聊天。
- **当前文件夹**：推荐优先取当前终端标签所绑定笔记的父目录；首次调用时取调用笔记的父目录；从文件夹菜单调用时取明确选择的文件夹。无文件上下文时先显示目录选择，默认候选为知识库根目录。新建操作开始时固定目标目录，不因随后切换页面而改变。

“任意 Agent”表示具备通用启动与交互入口，不表示所有程序无需适配即可生成完全相同的结构化对话。PTY 也不能揭示 Agent 未输出的内部内容。

对频繁重绘的程序，原始日志是内容保全依据；Markdown 是可读投影。不能仅删除 ANSI 控制符就宣称已经获得完整、无重复的对话。若“完整可读”必须指所有 Agent 均能精确还原提问、回答和工具结果，则需按 Agent 逐个适配，不能对未知程序承诺该效果。

原始输出日志默认不另行保存键盘原始输入事件。Shell 或 Agent 显示出来的输入可进入记录；不回显的输入不能据此推断。输入记录方式及对无回显提示词的支持须在设计时单独处理，避免把密码和所有按键无差别写入日志。

## 3. 用户故事

- 作为用户，我希望在当前笔记中启动我的 Agent，留在 Obsidian 内完成交互。
- 作为用户，我希望每篇笔记只有自己的会话，切换笔记时记录不会混在一起。
- 作为用户，我希望在一个插件窗口中打开多个终端标签，同时运行不同对话，并随时切换。
- 作为用户，我希望点击新增标签就能在当前文件夹得到新笔记，默认递增命名，之后可以直接改名。
- 作为用户，我希望内容随对话自动保存，关闭后能用普通 Markdown 阅读。
- 作为用户，我希望启动失败或保存失败时知道原因，并能恢复已经落盘的记录。

## 4. 功能需求与验收标准

### R1. 桌面端通用启动

- 当用户为一篇 Markdown 笔记启动会话时，插件应在该笔记页面中提供可输入、可滚动的嵌入式终端，并连接本机 Shell 或配置的 Agent 命令。
- 当用户从书签打开笔记、从文件列表打开笔记，或新建笔记后调用插件时，插件应按所打开的实际文件提供相同的会话入口；书签本身作为导航入口，不另建一份会话数据。
- 当用户配置其他命令行 Agent 时，插件应允许填写程序路径、参数和工作目录，不要求插件新增一个固定品牌按钮才能启动。
- 当路径包含空格、中文或非 ASCII 字符时，插件应按独立的路径和参数处理，不通过不可靠的字符串拼接启动程序。
- 当程序不存在、工作目录不可用或终端运行组件不匹配时，插件应显示具体原因和修复入口。
- 在移动端，插件应标记为不支持；系统及 CPU 架构的实际支持清单须根据后续测试公布。

### R2. 一篇笔记绑定一个逻辑会话

- 当笔记首次启动终端时，插件应创建稳定的会话标识并与该笔记绑定。
- 当同一笔记被重复打开或再次执行启动命令时，插件应重新连接已有运行实例，避免创建重复进程。
- 当用户在其他笔记启动会话时，插件应建立独立会话；各自的输入、输出和归档不得串写。
- 当用户切换活动页面时，已有输出应继续写入原绑定笔记，不使用“当前活动文件”作为持续写入目标。
- 当笔记重命名或移动时，插件应保留绑定；当笔记被复制时，插件应识别重复标识，避免两个文件控制同一会话或争写同一记录。
- 当绑定笔记被删除时，插件应停止向该路径写入并保留可恢复日志，不擅自重建用户删除的笔记。

### R3. 真实终端交互

- 当程序请求交互输入时，插件应支持中文输入法、粘贴、多行输入、方向键、Tab、Ctrl+C 中断及窗口缩放。
- 当 Agent 展示菜单、确认提示或重绘界面时，插件应通过 PTY 提供交互，而非仅使用一次性的命令执行框。
- 当输入焦点位于终端或笔记时，快捷键应按对应区域分发。
- 程序安装、登录及其账户使用由用户本机环境提供；插件负责启动、交互和记录。

### R4. 自动持续保存

- 当终端收到输出时，插件应按顺序持续记录，不依赖用户手动复制、导出或结束会话后才保存。
- 在正常本地磁盘条件下，笔记更新延迟目标不超过 1 秒；具体节流和高输出量处理在设计阶段确定并验证。
- 当用户正常停止会话或插件正常卸载时，插件应完成最后一批输出和笔记的保存，再显示保存完成。
- 当笔记更新失败时，插件应保留日志、显示待同步状态并允许重试；当日志也无法写入时，不得继续显示“已保存”，应明确提示并限制继续接收无法归档的数据。
- 当用户编辑原笔记时，插件应仅修改自己管理的会话记录区域，保留用户正文；区域被删除或产生冲突时，应保留待同步内容并提示恢复。
- 当 Obsidian 非正常退出后重新启动时，插件应检测可用日志并重建尚未同步的笔记内容。异常断电或进程强杀时尚未落盘的尾部数据不作零丢失承诺。

### R5. 完整记录与长期可读性

- 当输出包含颜色、光标移动、回车覆盖或清屏指令时，笔记中应显示对应的可读文字，不出现裸控制字符。
- 当程序重绘进度或使用替代屏幕时，插件应保留原始输出事件，生成可理解的文字记录或明确标记的界面快照；不得只保留退出时最后一屏并将其称为完整历史。
- 当内容包含 Markdown 标题、反引号、代码、中文或错误信息时，保存格式应保留其内容且不破坏笔记结构。
- 当会话很长时，记录不得因为终端滚动缓冲区达到上限而被截断。
- 当插件被关闭或卸载后，已写入的 `.md` 应仍可正常阅读、搜索和引用，不依赖专有视图。
- 原始日志应有明确关联入口；Markdown 中应记录启动时间、程序、工作目录、会话状态和保存进度。
- 对结构化对话的增强适配，应说明所支持的 Agent 与日志格式；未适配程序不得把猜测出的角色分类标成准确结果。

### R6. 关闭、停止与重新打开

- 当用户仅关闭笔记标签页或切换页面时，推荐保留会话运行及持续保存；重新打开应连接同一运行实例。
- 当用户关闭插件内部的终端标签时，推荐仅收起该标签并保留后台会话与保存；界面应清楚标注这一行为，并提供“重新打开运行中的会话”入口及“结束并关闭”操作。关闭标签不删除对应笔记。
- 当用户主动点击“结束会话”时，插件应停止对应进程，保存尾部记录并保留该笔记供查看。
- 当 Obsidian 正常退出或插件被停用时，首版推荐结束子进程并保存记录，不引入常驻系统服务。
- 当 Obsidian 重新启动并打开历史笔记时，插件应先展示已保存记录，不仅因打开笔记就自动执行其中的命令。
- 当用户请求继续对话时，若 Agent 有可用的会话恢复能力及标识，插件可据此恢复；否则应明确说明将启动新的进程，不能把可读笔记恢复等同于模型上下文恢复。
- 一篇笔记对应一个逻辑会话。已经结束的会话若无法原生恢复，新的对话应默认创建新笔记，避免把不同对话悄然混成一场。

### R7. 浏览器式多标签与并行会话

- 当用户打开插件窗口时，插件应显示终端标签栏、当前标签的终端及可见的“+ 新建终端页面”入口，提示可以增加多个标签。空状态也应提供建页入口，不强制反复弹出教学提示。
- 当首次从现有笔记调用时，推荐将该笔记作为首个标签；当它已经有运行会话时应复用原会话。只有明确新增标签时才自动新建文件，避免首次调用就产生多余文件。
- 当用户点击“+”时，插件应先成功创建目标目录中的笔记并建立唯一绑定，再建立对应标签及独立终端会话。默认沿用当前标签的启动配置；用户可在启动前选择其他配置。仅打开历史笔记仍遵循 R6，不自动执行历史命令。
- 当多个标签同时运行时，各自应拥有独立进程、终端状态、输入流、输出日志和保存进度；标签切换只改变当前查看与输入的会话，不中断其他会话。
- 当用户切换或拖动标签时，插件应保持每个会话的终端内容、滚动位置及文件绑定，输入只能发送到当前获得焦点的标签。
- 当标签显示时，标题应与对应笔记文件名保持一致，并可区分运行、已结束或保存失败等状态；状态不得仅因标签失去焦点而显示为已停止。
- 当用户选择“在 Obsidian 中打开对应笔记”时，插件应定位到实际文件，便于查看文字记录、搜索和引用。
- 当 Obsidian 正常退出后重新打开时，插件应恢复标签对应的文件、名称和顺序，并展示历史记录；是否重启 Agent 仍由用户明确触发。
- 首版应支持多个同时运行的标签，不将界面限制为单个会话；实际并发能力与资源边界应由测试说明，不承诺无限进程。

### R8. 同目录建文件与递增命名

- 当用户新增终端标签时，插件应在“当前文件夹”中创建真实的 `.md` 文件，初始名称依次为“终端页面一.md”“终端页面二.md”“终端页面三.md”，十之后继续正常递增。
- 当当前目录中已有同名文件或文件夹时，插件应递增寻找可用名称，不覆盖现有项目；连续或快速点击新增时，各次创建也应得到唯一文件。
- 每个目录应维护自己的命名序号，重启后继续递增；用户重命名、删除或关闭已有页面不应使已分配的序号立即回退复用。具体状态存储方式在设计阶段确定。
- 当用户通过标签的“重命名”操作修改名称时，插件应重命名对应的实际笔记，并保留会话、原始日志和持续保存的关联；从 Obsidian 文件列表改名也应同步更新标签。
- 当用户输入无效文件名或与现有项目冲突的名称时，插件应提示原因并保留原文件和会话，不静默覆盖。
- 当绑定笔记被移动时，插件应继续向该文件保存；随后从该标签新增页面时，推荐使用移动后的父目录。
- 当用户没有文件上下文、打开的是非 Markdown 页面或书签指向的并非一个可绑定笔记时，插件应让用户选择目标目录并创建终端页面，再建立标签；不改写原内容类型。
- 默认终端工作目录应采用对应笔记所在文件夹；当启动配置明确指定其他工作目录时，界面应展示该目录。记录文件所在目录与程序工作目录应能被用户分辨。
- 当新文件创建失败时，插件应保留已有标签并显示原因，不先启动一个没有归档目标的新会话；文件已经创建而进程启动失败时，应保留笔记并提供重试入口。

### R9. 用户自行选择和设置 Agent（0.2.0）

用户明确表示：“后期可以自己确定用哪个agent，并进行设置最好”。0.2.0 已实现以下增强，实际平台通过范围以验证记录为准。

- 当用户打开 Agent 设置时，应能选择预设或添加自定义命令行 Agent，并编辑名称、程序路径、启动参数和工作目录。
- 当用户检测某个配置时，应显示本机程序是否可用及实际版本；预设不得被当作该 Agent 已通过完整适配的证据。
- 当用户创建新标签时，应能选择此次使用的 Agent，也能使用自定的默认配置；不同标签可同时使用不同 Agent。
- 当同一个 Agent 需要多套参数或模型偏好时，应允许建立多个独立配置。
- 当用户调整默认 Agent 或编辑/删除配置时，应保留旧笔记、运行中进程及会话的原程序信息；历史记录不得被悄然切换给另一种 Agent。
- 当用户在已有会话中选择另一种 Agent 时，应通过新建会话笔记开始，保留原笔记的绑定；不同 Agent 的上下文不宣称能够自动互通。
- 当某个 Agent 有已验证的模型选择或配置入口时，可提供对应设置；未知 Agent 继续使用自定义参数和原生配置，不假定存在统一的模型、API Key 或恢复接口。
- 模型凭据由对应 Agent 的受支持配置机制管理，不把凭据写入会话 Markdown；插件不得从终端画面猜测密钥或要求用户在聊天中提交密钥。

### R10. OpenCode 首个增强适配（0.2.0）

用户已选择 OpenCode 作为首个适配对象，因为希望方便使用不同模型。OpenCode 是首个增强预设；R9 的通用 Agent 选择能力仍是产品范围。

- 当用户选择 OpenCode 配置时，应检测实际程序路径、版本和可用能力，优先使用其已有提供商与模型配置。
- 当用户为笔记创建 OpenCode 对话时，应取得并保存该笔记专属的原生会话 ID；每个标签绑定自己的 ID，不能靠“继续最近一次会话”猜测归属。
- 当用户主动继续历史对话时，应使用明确绑定的原生会话 ID 恢复，并向原笔记追加记录；仅查看笔记不启动程序或发送提示词。
- 当可以获取结构化消息时，应以原生消息与片段 ID 去重，生成“用户输入、Agent 回答、工具执行及结果”的可读记录，折叠冗长工具输出；原始终端日志继续保留。
- 当界面断连或插件重载后重新同步时，应从原生会话补齐缺失记录，不重复已经归档的消息。
- 当 OpenCode 版本、原生会话或结构化接口不可用时，应保留通用终端记录并解释当前支持范围；不能从屏幕重绘猜测准确角色或静默绑定其他会话。
- 当用户选择其他 Agent 时，应按其实际适配能力提供通用记录或增强功能，不将 OpenCode 的参数与协议套用于其他 Agent。

## 5. 首版建议范围

包含：通用 Shell/Agent 配置、笔记页面内终端、浏览器式多标签、多个独立会话同时运行、同目录新建笔记、递增命名及同步重命名、持续原始输出归档、可读 Markdown、停止与重开、保存失败恢复。

终端回放是处理复杂重绘的补充，不能用“只能回放”替代 Markdown 文字记录。

首版不增加模型 API 接入、聊天账户系统、MCP 服务器、手机端或退出 Obsidian 后的常驻进程。这些不属于用户本次提出的四项核心目标。

0.1.0 未提供特定 Agent 的结构化日志适配。0.2.0 已实现 R9、R10：以 OpenCode 为首个增强适配对象，同时支持自行选择、设置其他 Agent，并继续提供通用终端入口。

## 7. 当前采用的核心边界

推荐采用“通用终端记录 + 原始输出归档 + 可逐步加入的 Agent 结构化适配”。如果用户要求“所有未知 Agent 均能自动得到逐轮、无重复、精确角色分类的完整笔记”，需要先调整承诺或限定 Agent；不能通过开发一个通用终端就保证实现。

多标签、同目录新增文件、默认递增命名及允许重命名已由用户明确要求，本轮直接纳入首版。首次调用绑定当前笔记、点击“+”创建同级新文件，以及按当前终端标签文件所在目录新建，属于本稿推荐交互细节。

关闭 Obsidian 页面标签或插件内终端标签时继续记录、退出 Obsidian 正常收尾的行为采用 R6 推荐方案，后续可根据实际工作方式调整。

## 8. 技术调查依据

以下是可行性依据，不是本插件已经完成的实现或测试证明。

- [node-pty 官方仓库](https://github.com/microsoft/node-pty)：支持 macOS、Windows，提供伪终端进程读写；Windows 使用 ConPTY。
- [xterm.js 终端缓冲区文档](https://xtermjs.org/docs/api/terminal/interfaces/ibuffer/)：终端包含普通及替代缓冲区，当前缓冲区不等同于完整历史日志。
- [Obsidian Vault API](https://docs.obsidian.md/Plugins/Vault)：笔记读写及 `Vault.process()` 的并发修改保护；编辑器内容和外部程序同时修改仍需在设计中处理。
- [Steward Shell/Terminal 文档](https://github.com/googlicius/obsidian-steward/wiki/Shell-command-and-Terminal)：区分普通文本输出与 PTY 交互终端，说明通用模式的交互需求。

## 10. 0.3.0 用户测试反馈与修正

### R11. 右侧上下工作台

- 当调用插件时，工作台应位于当前中央文档右侧的 Obsidian 原生侧栏，保留中央文档。
- 当右侧栏左右边界拖动时，应由原生分隔线调整侧栏/中央文档宽度，终端列数随可用宽度重新适配。
- 右侧上方展示备份，下方为可交互终端；上下比例可调，重载保留。较小窗口应滚动而不相互覆盖。
- 升级时旧中央工作台可迁入右侧；迁移/重载不会仅因展示历史就启动程序。

### R12. 系统 Shell 与任意 CLI

- 全新安装和旧版升级后的新标签都直接使用系统 Shell，无需选择或配置某种 Agent。
- macOS 使用用户登录 Shell；Windows 使用 PowerShell，允许用户在设置中自定义 Shell 路径/参数。
- 用户可在终端直接执行已安装的 OpenCode、Claude Code、Codex CLI 等命令；不默认创建 OpenCode 私有服务。
- 保留旧版历史与启动快照，只有明确请求历史恢复时才调用旧增强适配。新标签不继承旧 Agent 配置。

### R13. 同目录新备份与本地导出

- 从普通文件调用时，应在该文件父目录新建独立 Markdown 备份；不把记录写入来源文档正文。
- 沿用每目录「终端页面一/二/三」递增、跳过重名、可重命名、一标签一备份的规则。
- 同一来源重复调用尚在运行/待启动的会话应复用已有备份；主动新增始终创建新文件与独立会话。
- 来源或备份改名/移动时更新关联，备份日志和会话不串写。关闭视图继续后台记录；停止后保留完整落盘笔记。
- 提供「导出 Markdown」；原生保存对话框选择本地位置，取消不写；写入失败保留已有目标文件，成功文件无需插件即可阅读。

### R14. 紧凑字号与独立配色

- 终端和记录区默认各 12px，分别可调；记录标题不得套用中央文档的大号标题导致遮挡。
- 终端默认黑底浅字，记录区默认跟随 Obsidian。两区各自提供跟随主题、黑色、灰色、浅色及自定义背景/字色。
- 修改设置后对已打开的终端和记录立即生效；重载后仍保留，两个区域互不覆盖。
- 使用 Obsidian 原生字体、图标和可访问控件，窄侧栏工具栏不强制撑大或遮挡正文。

## 11. 0.3.1 增量对话记录（用户确认）

### R15. 增量输出与重绘去重

- 当终端新增输出时，应持续更新当前输出块，普通换行保留顺序；流式字词扩展、清屏、光标重绘、颜色/高亮切换不得反复追加整个画面。
- 当内容仅为尚未提交的输入、选择光标或动画时，不应生成新的对话记录。不同轮次合法的相同输入/输出不得全局去重。
- 当屏幕滚动、尺寸变化或反复重绘历史内容时，已归档内容不得重复；原始输出日志继续完整持久化。
- 当重载或不同频率保存时，同一份日志应得到一致的可读记录；render 不生成新事件。

### R16. 可见输入与程序输出分开

- 当用户提交可见命令或消息时，标为「我」；程序结果标为「终端」，菜单确认等非文本操作标为「操作」。不假定任意CLI具有助手角色。
- 输入草稿、退格和光标修改应在提交时合并；输入回显不作为另一份回答重复保存。
- 不回显的密码及仅显示掩码的输入不得作为用户文本归档；不记录原始按键流。仅经终端显示确认的提交内容可成为持久输入事件。
- 输入/输出事件应有持久化顺序，关闭和重载不得丢失已确认的输入或改变归属。
- 通用全屏TUI使用显示差异和操作边界，不承诺恢复屏幕从未展示的消息或所有未知Agent的原生角色；对无法确认属于输入回显的裸边框同文行优先保留输出，允许含输入回顾文字，避免误删回答；已存在原生消息可优先使用其结构化内容。

### R17. 历史兼容与精简副本

- 既有笔记默认保留其原投影版本，不在升级时直接改写唯一原件；新会话使用增量格式。
- 当用户选择「生成精简记录副本」时，从完整日志生成同目录新Markdown，保留原笔记及日志；旧日志无法确认的输入不得猜测标为用户消息。
- 故障/损坏日志不得作为完整来源生成成功副本。已有外观、侧栏、文件绑定及多标签规则保持。
